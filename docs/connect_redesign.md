# Проект: page-first reconnect

Цель — спека пользователя: «открыл кейс — наушники подключились СРАЗУ ЖЕ;
не могут — повторяют; переоткрыл — повторяют снова».

## Диагноз (из `docs/manual_connect_path.md`)

Ручной путь работает, потому что хост **пейджит пира** (`HCI 0x0405` +
исходящие `L2CAP ConnReq`). Программа пейджить не умеет: её единственный
примитив, `BluetoothSetServiceState`, — локальный флип состояния сервиса,
дающий ноль HCI. Тоггл DISABLE→ENABLE переустанавливает драйвер, но
драйвер ≠ страница. Вывод: в reconnect-путь нужен исходящий примитив —
пейджинг, а не флип.

## Идея

Заставить стек создать ACL к пиру из user-mode. Штатный способ на Windows —
`connect()` на `AF_BTH`-сокете: стек сам пейджит пир (шлёт `0x0405`), а
дальше установленные профильные драйверы (`btha2dp` и др.) делают свои
`L2CAP ConnReq` — ровно как в ручном захвате. Сокет после коннекта сразу
закрывается: нужен только ACL, канал не нужен.

Цель для `connect()`: L2CAP PSM `0x0001` (SDP). Причины: фиксированный PSM,
есть всегда, профильно-нейтрален (не дёргает аудио). Даже отказ на уровне
протокола нас устраивает — страница и ACL уже созданы к этому моменту;
факт страницы подтверждается событием Policy (`Operational` включён,
см. `manual_connect_path.md`).

Запасной вариант, если SDP-PSM упрётся в причуды стека/донгла: RFCOMM
`connect()` на HFP-канал пира (канал узнаётся из SDP). Порядок пробовать:
SDP PSM → RFCOMM HFP → оставить как есть (тоггл-лестница).

## Архитектура (зеркалит `connect.rs` / `connect_fsm.rs`)

- `src/page_fsm.rs` — чистая логика: лимит частоты страниц, классификация
  исходов, ноль Win32. Тестируется фейком вне Windows, как `connect_fsm`.
- `src/page.rs` — тонкий Win32-клей: берёт `Address` пира из
  `BLUETOOTH_DEVICE_INFO` (уже есть в poll loop), делает сокет-`connect`,
  возвращает квитанцию. Квитанция, не линк: доказательство — только
  следующий `fConnected`.
- `src/sys/ws2_32.rs` — новые биндинги: `WSAStartup`/`WSACleanup`,
  `socket`, `connect`, `closesocket`, `select`, структура `SOCKADDR_BTH`.
  Грузить из System32, как `bthprops.cpl` (та же анти-hijack дисциплина).
- `config.rs` — константы `PAGE_*`: минимальный интервал между страницами,
  кап ожидания `connect()` (non-blocking + `select`, 5 с — `PAGE_CONNECT_TIMEOUT_MS`), порог
  «пир совсем не отвечает» для отката на тоггл-лестницу.

## Место в `worker.rs`

Страница — **первой**, до тоггл-лестницы, на проходе с упавшим линком:

1. страница по своему лимиту (пейджинг каждые N секунд, не каждый опрос —
   страница это радио-churn);
2. исходы `Paged` / `PageFailed` / `PeerUnreachable` обновляют состояние
   зеркально существующим рукам (`next_connect_ms`, `connect_fails`,
   breaker'ы);
3. тоггл-лестница (R1–R4, `drive_connect`) остаётся **фолбэком** без
   изменений — на случай «ACL есть, а профили встали»;
4. debt-логика не трогается: страница не снимает драйверы, маркеры не нужны.

Комментарий-предположение в `connect_fsm.rs` («fresh install pages the
peer», тесты `FakeStack::set_state`) захватом опровергнут: переустановка
драйвера странице не равна. При реализации поправить формулировки там,
иначе код будет врать читателю.

## Полевой итог (2026-10-02, реализовано)

Проект реализован; поле переписало две гипотезы.

1. **L2CAP через Winsock недоступен на этом стеке.** `--page-probe` дал:
   `l2cap-psm` и `l2cap-uuid` — синхронный отказ `10050 WSAENETDOWN` прямо в
   `connect()` (на воздух не уходит ничего, HCI пуст), `rfcomm-uuid` —
   асинхронный исход (таймаут = страница реально ушла, пир не ответил).
   Вывод: пейджим **RFCOMM** на HFP HF (`0000111E`), стек сам делает SDP-резолв
   канала и страницу. L2CAP оставлен в зонде как tripwire.
2. **Сокет нельзя закрывать после страницы.** Линк жил ровно ~3 с (ACL) при
   «20 с» в логе (лаг кэша `fConnected`): ETW показал `HCI_Disconnect` от
   хоста через 3.08 с после страницы — ровно окно settle. Закрытие последнего
   DLC роняет ACL. Поэтому успешная страница держит сокет до конца эпизода;
   новый сокет заменяет старый только после того, как создан (хотя бы один
   DLC всегда открыт).

Дальнейшая полева причина «линк есть, звука нет» оказалась не в коде
пейджинга: A2DP-эндпоинт не регистрировался в MME (в waveOut только FxSound и
монитор), keepalive стримил в пустоту, пир ронял ACL каждые 20.016 с.
Регистрация починилась физическим перевтыком донгла (см.
`csr-bluetooth-debugging`: у клонов CSR `pnputil /restart-device` не снимает
VBUS, лечит только power cut). После перевтыка эндпоинт #0 встал — линк
держится, звук есть.

## Временные диагностики

`wake-trace` и `peer-probe` в `worker.rs` — временные, своё отработали.
При реализации: `peer-probe` сжать до slim-версии (лог только перехода
`LastSeen`, без атомиков на каждый опрос) или убрать — Policy-событие и
`fConnected` уже дают корреляцию; `wake-trace` убрать полностью.

## Верификация (без ETW-шума)

1. `cargo test` — весь набор зелен, плюс новые `page_fsm`-тесты на фейке;
2. полевая проверка по спеке: закрытый кейс → открыть → линк;
   сверка по трём часам: `btf.log` (страница запрошена), Policy-событие
   (`connection ... successfully established`), `fConnected` в опросе;
3. целевой бюджет: страница → профили ≈ 1–2 с (как в ручном захвате
  17:42:27–17:42:28), а не минуты;
4. отрицательный контроль: страница при закрытом кейсе обязана fast-fail
   по таймауту, а не вешать poll loop (проверяется строкой BLOCKED в логе —
   её не должно быть);
5. HCI/L2CAP-каналы включать только если Policy + лог разойдутся.

## Риски

- Пир в глубоком сне может не ответить на страницу с первого раза —
  для этого страница повторяется по своему лимиту (п. «повторяют» спеки),
  а не однократно;
- причуды CSR-донгла к L2CAP-сокетам — проверять полем, фолбэк RFCOMM
  держать готовым;
- страница каждые N секунд при открытом кейсе без наушников рядом —
  лимит + `PeerUnreachable` backoff, чтобы не жечь эфир;
- [Гипотеза, ~60%] удерживаемый RFCOMM-DLC на HFP HF может занимать тот самый
  канал, который нужен родному HFP-драйверу Windows: тогда hands-free профиль
  (звонки) не поднимется, пока сокет удерживается, при живом A2DP. Симптом
  проверять только на реальном звонке; если подтвердится — пейджить другим
  RFCOMM-сервисом пира или отпускать сокет, как только `fConnected` встал;
- что НЕ трогаем: debt-маркеры, R1–R4, MMDevice-опрос, тоггл-путь
  (он остаётся фолбэком, его тесты должны остаться зелёными).
