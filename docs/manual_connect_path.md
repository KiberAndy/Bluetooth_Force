# Ручное подключение: что именно происходит и почему

Запись от 02.10.2026. Вопрос: каким методом подключаются наушники, когда
пользователь жмёт «Подключить» вручную. Ответ доказан захватом HCI/L2CAP,
а не догадками.

## Короткий ответ

Ручное подключение = **хост пейджит пир**: `HCI_Create_Connection (0x0405)`
на адрес `94:8B:93:B1:E4:A1`, затем пачка исходящих `L2CAP ConnReq`
(PSM `0x01` SDP, `0x19` AVDTP, `0x17` AVCTP). Страница → профили за ~1.4 с.
Метод программы (`BluetoothSetServiceState ENABLE`) в этом захвате даёт
**ноль HCI/L2CAP** — это локальный вызов, до пира он не доходит.

## Чем записано

- Каналы (все по умолчанию выключены, включались точечно):
  - `Microsoft-Windows-BTH-BTHPORT/HCI` — команды хоста и события контроллера;
  - `Microsoft-Windows-BTH-BTHPORT/L2CAP` — L2CAP-пакеты в обе стороны;
  - `Microsoft-Windows-Bluetooth-Policy/Operational` — вердикт стека
    («connection successfully established»).
- Провайдеры проверялись через `logman`, каналы — через `wevtutil`;
  пустая ETW-сессия через `logman` ничего не дала (только заголовки, 8 КБ).
- Направления пакетов достоверны: L2CAP `id264` (`PB=10`) = хост→контроллер,
  `id263` = контроллер→хост; HCI `Type 1` = команда хоста, `Type 2` = событие
  контроллера.

## Disconnect (17:42:13–17:42:14, для контраста)

- 17:42:13.434 — три `L2CAP DisconnReq` (иденты 33–35): рвутся сигнальные
  каналы;
- 17:42:14.514 — хост шлёт `HCI_Disconnect (0x0406)`, handle `0x80`,
  reason `0x13` (Remote User Terminated);
- 17:42:14.550 — `Disconnection_Complete`, reason `0x16` (Connection
  Terminated by Local Host), ACL падает.

Разрыв — тоже активная команда хоста, а не «само отвалилось».

## Connect (17:42:27–17:42:28)

- 17:42:27.303 — хост шлёт `HCI_Create_Connection (0x0405)` на адрес
  `A1 E4 B1 93 8B 94` = `94:8B:93:B1:E4:A1` (наушники). **Хост пейджит пира.**
  Кейс к этому моменту был открыт давно — пир слушал;
- 17:42:28.365 — `Connection_Complete`, status `00`, handle `0x80`:
  страница принята за ~1 с;
- 17:42:28.484–28.668 — пачка `L2CAP ConnReq`: PSM `0x01` (SDP, хост),
  `0x19` (AVDTP), `0x17` (AVCTP), затем Config и SDP-запрос — всё с успехом;
- 17:42:28 — событие Policy: `connection to 0x948B93B1E4A1 successfully
  established`.

Дальше обычная жизнь линка: уход в sniff 17:42:55, выход из sniff и
стриминг с 17:44.

## Почему метод программы не работает

`BluetoothSetServiceState(ENABLE)` на уже включённый сервис отвечает
`E_INVALIDARG`/`0x57` и ничего не делает — это видно и в `btf.log`
(отказы по A2DP/HFP/AVRCP), и в коде (`src/connect_fsm.rs`: классификация
`AlreadyInState`). Захват даёт вторую половину доказательства: в отличие
от ручного пути, вызов программы **не порождает ни одного HCI/L2CAP**.
Локальный флип состояния сервиса ≠ страница пиру.

Отсюда же объяснение прошлых «успехов» программы: линк вставал через
минуты после тогглов, когда наушники были вне кейса и сами ретраили —
программа совпала с их ретраем на фоне собственного churn'а, а не
допейджила их через `ENABLE`. Это вывод по корреляции, не прямое
доказательство (прямое — только ноль HCI от `ENABLE` в этом захвате).

Связанное полевое наблюдение (лог peer-probe 17:21:45–17:25:04): с открытым
кейсом стек 140 секунд не видел пира вообще (`LastSeen` застыл на
17:09:11, ни одного чужого события дерева устройств). Пир становится
виден, только когда его пейджат — сам он хосту не объявляется.

## Оговорка

Захват — переподключение бодрствующих наушников (disconnect→connect из
настроек), а не пробуждение из глубокого сна в кейсе. То, что страница
срабатывает именно из сна, этим файлом не доказано — но доказано, что
*только* страница вообще что-то делает, а `ENABLE` — ничего.

## Состояние системы после захвата

- Каналы HCI и L2CAP **выключены обратно** (шумные);
- `Bluetooth-Policy/Operational` **оставлен включённым** сознательно:
  одно событие на коннект, годится для корреляции меток времени
  с `btf.log` без ETL-шума.
